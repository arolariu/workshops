# Phase 4 · Lab 04: MCP servers, five tiers

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Lab 04's homework ladder per spec §5.4: grow 🟡 medium "Add a tool" (30–45 min) and 🔴 hard "A tool that changes things" (1–1.5 h), and add 🟣 hard+ "Untrusted output" (1.5–2 h) and 💎 hard++ "MCP from the protocol up" (2–3 h), each in the ticket format with milestones, hints, takeaway, quiz and going further.

**Architecture:** Each tier starts from the reference result of the tier before it (`src/` = predecessor `sol/` + this level's starter files). The portal server (`mcp/studybuddy-server.mjs`) grows from a validated read tool (medium) into a safe, idempotent, atomically persisted write tool with a contract suite (hard), then serves untrusted student posts behind a server-side token (hard+, a new `mcp/board.mjs`). Hard++ builds a second server (`mcp/library-server.mjs`) from raw JSON-RPC, over stdio and HTTP, with a conformance suite. Checks talk to the servers through the kit's real MCP client (`t.mcp`, initialize handshake included); hard++ uses its own raw client (`tests/helpers.mjs`) because it must send what the kit's client can't (cursors, cancellations, broken JSON, HTTP).

**Tech Stack:** Node 22+ ESM, `node:test`, `node:http`, `node:crypto`, global `fetch`, the check kit. No npm dependencies (the learner writes MCP without an SDK).

**Spec:** `docs/superpowers/specs/2026-10-18-agent-harness-workshop-experience-design.md` §5.4 (Lab 04 row, threads, "Under the hood / In the enterprise"), §5.3, §5.1, §5.2 (`bring`), §5.10; overview plan `docs/superpowers/plans/2026-10-19-phase-4-ladders.md`; exemplar `docs/superpowers/plans/2026-10-19-phase-4-lab-05.md`.

## Global Constraints

See the overview plan. Lab-specific (coordinator's kickoff):

- `bring` carries `mcp/**` and `.mcp.json` into every later level: keep `.mcp.json` entries working and fast, keep the portal's tools compatible.

## MCP facts this lab relies on (evidence, 19–20 Oct 2026)

- **Copilot CLI negotiates protocol `2025-11-25` with an `initialize` handshake.** Evidence (read-only, free): Copilot's own logs (`~/.copilot/logs/process-*.log`, CLI 1.0.99-2) record `[rust:rmcp::service] Service initialized as client {"peer_info":"Some(ServerPeerInfo { protocol_version: ProtocolVersion(\"2025-11-25\"), … server_info: … name: \"studybuddy-portal\" …` and the StudyBuddy server echoes the client's requested version, so 2025-11-25 is what Copilot asks for. Failing servers log `MCP lifecycle negotiation did not complete within 60000 ms`. Some servers answer `2026-07-28` and Copilot accepts that too.
- **The current MCP revision is `2026-07-28`**, which removes `initialize`/`notifications/initialized` and `ping`, adds a mandatory `server/discover`, `resultType` on results, `ttlMs`/`cacheScope` on list results, and drops Streamable HTTP sessions (https://modelcontextprotocol.io/specification/2026-07-28/changelog). This lab follows **2025-11-25** (https://modelcontextprotocol.io/specification/2025-11-25): lifecycle, pagination (`cursor`/`nextCursor`, invalid cursor → `-32602`), cancellation (`notifications/cancelled`, no response for a cancelled request), tools (`isError` for input validation, protocol errors for unknown tools; annotations `readOnlyHint`, `destructiveHint` (default true), `idempotentHint`, `openWorldHint`), resources (not found → `-32002`), prompts (bad name or missing argument → `-32602`), `_meta` key prefixes (reverse DNS; `…modelcontextprotocol…`/`…mcp…` second labels reserved), Streamable HTTP (POST per message, `Accept`, `202` for notifications, `405` for GET without SSE, `Origin` check → `403`, bind to 127.0.0.1, `MCP-Protocol-Version` header → `400` when unsupported, sessions optional).
- **Copilot passes only `PATH` to a stdio server;** every other variable must be in the server's `env`, which supports `$VAR`, `${VAR}` and `${VAR:-default}` (https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-mcp-servers and the CLI command reference, "Local server configuration fields"). `copilot mcp get <name> --json` shows the configured env unexpanded and does **not** start the server (spike, 20 Oct 2026, CLI 1.0.101-0, free), so expansion could not be observed without a paid session.
- **Copilot saves any tool output over 20 KiB to a file** and gives the model a path and a preview (`COPILOT_LARGE_OUTPUT_THRESHOLD_BYTES`, https://docs.github.com/en/copilot/concepts/prompting-and-context/context-management). MCP tools included.
- `copilot --help` (1.0.101-0): `--secret-env-vars` strips named variables from shell and MCP server environments and redacts their values from output; `--allow-all-mcp-server-instructions` includes servers' `initialize.instructions` in the system prompt "instead of only allowlisted servers"; `--additional-mcp-config <json|@file>` adds servers for one session.

## Deviations from the spec

| Spec | This plan | Why |
|---|---|---|
| Hard++ "initialize and capabilities" | Implemented as in MCP **2025-11-25** (initialize + `notifications/initialized` + `ping`). `server/discover` (2026-07-28) is a 🚀 Going further item. | The current MCP revision (2026-07-28) has no `initialize`, but Copilot CLI negotiates 2025-11-25 with `initialize` (Copilot logs above). The lab follows what the learner's real client speaks. |
| Hard++ "an HTTP transport" | Streamable HTTP without sessions (no `Mcp-Session-Id`), JSON responses only (no SSE), `GET` → `405`. Init-before-use is enforced on stdio only. Cancellation is tested over stdio. | 2025-11-25 makes sessions optional ("MAY assign") and SSE optional; 2026-07-28 removes sessions. Without a session an HTTP request can't be tied to a handshake or to a pending call. |
| Hard++ "a shipped conformance suite" | The learner ships `mcp-conformance.test.mjs` with the server; the checks run it on the learner's server and on six protocol mutants built at check time (it must fail on each). | "Prove it" like Lab 05 hard: a suite that never fails proves nothing. |
| Hard++ "a versioned tool schema with a deprecation" | `search_courses` carries `_meta["dev.studybuddy/schema-version"]: 2`; the v1 tool `find_courses({ q })` stays listed as **Deprecated** (description, `_meta["dev.studybuddy/deprecated"]` with `replacedBy` and `removeAfter`), still works, and every result says so. | MCP has no tool versioning; `_meta` with a reverse-DNS prefix is the spec's extension point, and keeping the old name working for a window is how a published tool changes without breaking cached tool lists (Copilot snapshots local servers' tools). |
| Hard "idempotency" | Marking an assignment that is already done **succeeds** with `changed: false` (the old check expected `isError` "already done"). | A write tool must be safe to retry: models and clients repeat calls. An error on a retry makes the model believe the first call failed. |
| Hard "atomic writes" | Checked behaviourally: the server runs with `node --import tests/fs-spy.mjs`, which logs every write-like `fs` call; `state.json` must only ever be the target of a rename from a file in the same folder. A corrupt state file must never be overwritten. | Partial writes are too rare to observe in a test; the write pattern is what makes them impossible. |
| Hard "contract tests run through a real MCP client" | The learner writes `mcp-contract.test.mjs` (plumbing given: a 40-line stdio MCP client with the handshake); the checks run it on the learner's server and on six mutants of the reference server. The checks themselves use the kit's MCP client. | Same reason as hard++; and the kit's client is the "real client" for the checks. |
| (as built) Suites at the src root, not in `mcp/` | `mcp-contract.test.mjs` and `mcp-conformance.test.mjs` live next to the app's tests. | `mcp/**` is a harness path: `bring` would carry a filled-in suite into Lab 05+, where `npm test` runs it (Lab 05 hard runs tests after every edit) while the data files it needs (unchanged starters) never travel. App files never travel, and `npm test` still runs the suites in Lab 04. |
| Hard+ "authenticate with a server-side token" | The token is `STUDYBUDDY_BOARD_TOKEN`, read by the server; `.mcp.json` maps it with `"${STUDYBUDDY_BOARD_TOKEN:-}"`; the board API is a given in-process stand-in (`portalBoardApi`) that checks the token's SHA-256 and, like some real APIs, **echoes a bad token in its error body**. | Copilot passes only `PATH` to stdio servers (docs). The empty default keeps the server starting in later labs where nobody set the variable. The echo is the trap that makes "never in an error" testable. |
| Hard+ "label where data comes from" | Only the board tool's result is wrapped (`{ source, trust: "untrusted", notice, course, posts }`); the official portal tools keep their shapes. | The earlier tools' outputs are a contract (medium and hard checks, and `bring` into later labs). |
| (as built) Hard+ the agent check's token | `setup` writes the demo token into the copy's `.mcp.json` env (a literal) instead of relying on `${…}` expansion. | The check tests the injection, not the expansion, which could not be observed for free (spike above). |
| Hard++ agent check | Copilot loads the second server for one session with `--additional-mcp-config @library.mcp.json` (written by `setup`); `.mcp.json` does not register it. | The kickoff: register the second server only if Copilot must load it. In later labs it would start a server nobody uses. |
