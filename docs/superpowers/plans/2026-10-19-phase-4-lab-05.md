## Hook facts this lab relies on (spike, 19 Oct 2026, Copilot CLI 1.0.99-2, 1 prompt; plus the hooks reference)

- **Order in `-p` mode:** `userPromptSubmitted → sessionStart → preToolUse → postToolUse → … → agentStop → sessionEnd`. The prompt hook fires *before* the session hook.
- **`sessionStart`** input: `{ sessionId, timestamp, cwd, source: "new"|"startup"|"resume", initialPrompt }`. Output `{ additionalContext }` reaches the model (the spike's "end with PELICAN" was obeyed).
- **`userPromptSubmitted`** input: `{ sessionId, timestamp, cwd, prompt }`. Command-hook output is **dropped**: it cannot block or rewrite a prompt. It can only record.
- **`preToolUse`** input: `{ sessionId, timestamp, cwd, toolName, toolArgs }`; `toolArgs` is an **object** in the real CLI (the kit sends a JSON string). Same `sessionId` across all events of a session.
- **`postToolUse`** fires after a **successful** call (`toolResult: { resultType: "success", textResultForLlm }`); a failed call fires **`postToolUseFailure`** with `error: string`.
- **Failure modes (hooks reference):** a command `preToolUse` hook that crashes or exits non-zero **denies** (fail closed); a hook that **times out is allowed** (fail open, even for policy hooks). So a guard must enforce its own deadline, well under `timeoutSec`, and deny when it runs out.
- **Org policy in real life:** machine-wide policy hooks in `/etc/github-copilot/policy.d/*.json` or `C:\ProgramData\GitHub\Copilot\policy.d\*.json`, loaded first and not disableable. The lab simulates the org layer with a file the security team owns.

## Deviations from the spec

| Spec | This plan | Why |
|---|---|---|
| Hard+ "a timeout fails closed" | The guard runs the engine in a worker and denies when its own deadline (1.5 s) passes; `timeoutSec` stays 10. | Copilot's own hook timeout fails **open** (hooks reference), so only the guard can make a timeout fail closed. |
| Hard++ "`userPromptSubmitted` hooks that … flag prompts" | The prompt hook records a flag (it cannot block); the guard puts a flagged session in **lockdown** (no shell or write calls except allow rules marked `"lockdown": true`). | Command-hook output of `userPromptSubmitted` is dropped. Layering gives the flag teeth. |
| Hard++ org policy "can't be overridden" | Repo `allow` rules may set `"override": true` to make exceptions to the **repo's own** denies; org denies win over everything. | Under "deny wins" alone, an override is impossible anyway; exceptions make the layering visible and testable. |
| Hard "table-driven test suite" | Plus **mutants**: the suite must pass on the reference guard and fail on six broken guards. | "Prove it": a suite that never fails proves nothing. |
| Medium audit report | Reads `guard.jsonl` (every call the guard saw, with its decision), not `audit.jsonl` | `postToolUse` only sees successful calls; denials never reach it. |
| (as built) Policy files in `.github/hooks/` | The policies live in `.github/hooks/policies/{repo,org}.json`, never directly in `.github/hooks/`. | Copilot loads **every** `.github/hooks/*.json` as a hook config: a policy file there is read as a broken hook config (found in the TUI smoke test). |
| (as built) Hard mutants as files | Built at check time from the reference guard (`tests/mutants.mjs`). | Six near-copies of the guard drift from the reference; anchored edits fail loudly when the reference changes. |
| (as built) Hard+ "deny wins" | A deny rule fires when **one** command of a call matches; an allow rule (and so an override or a lockdown exception) only when it matches **every** command. | Otherwise `npm test && rm -rf src` rides along on an allow rule for `npm test` (review finding, critical). |
| (as built) Hard++ lockdown "no shell or writes" | Lockdown is an **allow-list**: only reads, and calls a `"lockdown": true` allow rule covers completely. | A deny-list misses `web_fetch`, MCP tools and sub-agents (review finding). |
| (as built) Hard++ audit log | A repository rule denies changes to `.agent-logs/` (tools and shell); reads stay allowed. | A tamper-evident log the agent can rewrite and re-chain is only evidence against a careless agent (review finding). |
| (as built) Medium agent check | Setup removes the "never add dependencies" line from the copy's `AGENTS.md`. | With the soft rule present the model refuses on its own and the guard is never asked: the check measured the model, not the hook. |

**Interfaces (the policy format and engine API, given in todo.md):**

```text
policies/repo.json  { version: 1, default: "allow" | "deny", rules: Rule[] }
Rule         { id: /^[a-z0-9-]+$/, decision: "allow" | "deny", severity: "low" | "medium" | "high" | "critical",
               reason: string (required for deny), match: Match }
Match        all given keys must match (AND); regexes are case-insensitive:
               tool        "shell" | "write" | "read" | a tool name, or an array of those
               command     regex, tested against each normalised command ("delete --force --recursive build")
               commandLine regex, tested against the whole shell command (whitespace collapsed)
               path        regex, tested against each path the call touches (file tools' path; shell arguments)
               text        regex, tested against JSON.stringify(args)
```

```js
validatePolicy(policy) → string[]                       // problems; [] when valid
normalize(toolName, args) → { tool, kind: 'shell'|'write'|'read'|'other', commands: [{ name, flags: string[], args: string[], line }], commandLine, paths: string[], text }
evaluate(policy, call /* from normalize */) → { decision: 'allow'|'deny', rule: string|null, severity: string|null, reason: string|null, matched: string[] }
```

Normalised delete family: `rm`, `Remove-Item`, `ri`, `del`, `erase`, `rd`, `rmdir` (and PowerShell's `rm`/`del` aliases) → `name: 'delete'`, flags sorted from `--force`/`--recursive`: bash `-r -R --recursive -f --force` and combined (`-rf`, `-Rfv`); PowerShell `-Recurse` and its prefixes (`-r`, `-rec`) → `recursive` **and** `force` (PowerShell does not ask); `-Force`/`-fo` → `force`; cmd `/s` → `recursive`, `/q` → `force`. Wrappers unwrapped (depth ≤ 3): `sudo [-flags]`, `env`, `VAR=value`, `command`, `exec`, `nohup`, `time`, `xargs [-flags]`, `bash|sh|zsh -c "…"`, `cmd[.exe] /c|/k "…"`, `powershell|pwsh [-NoProfile] -Command|-c "…"`, `Invoke-Expression|iex "…"`.

Evaluation: deny wins (the matched deny with the highest severity, ties by rule order); otherwise the first matching allow; otherwise `default`.

**Checks:**
- **M1 · The policy file**: your `policies/repo.json` passes your `validatePolicy` and the checks' own schema; `validatePolicy` returns at least one problem for each of the 7 broken policies in `fixtures/policies.json` (wrong version, unknown decision, duplicate id, deny without a reason, a regex that does not compile, an unknown match key, an empty match) and none for a minimal valid one.
- **M2 · The engine**: `evaluate` with a hand-made policy: deny beats allow on the same call; the highest severity wins; `default: "deny"` denies an unmatched call; the result names the rule. The guard uses the policy: every medium and hard corpus still gives the same decisions; the guard log line carries `"rule"`; and in a temp copy whose `policies/repo.json` gains a rule denying `echo`, the guard denies `echo hi` (so the rules live in the policy, not in code).
- **M3 · One command, many spellings**: `fixtures/spellings.json` (26 deny, 14 allow, including `grep -rf patterns.txt .`, `cp -rf a b`, `git rm -r --cached x`, `echo "rm -rf"` as traps) through the guard; `normalize('powershell', { command: 'rm -r -fo build' }).commands[0]` is `{ name: 'delete', flags: ['force', 'recursive'], … }`.
